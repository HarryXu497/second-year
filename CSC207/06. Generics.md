# Introduction

Generics are a feature in Java that allows for programmers to generalize the type(s) that a class or method uses. They allow us to reuse the same code for various input types without needing to cast things constantly.

For example, consider the `List<T>` interface built into Java. This interface specifies what it means for a class to store a list of objects of a generic type `T`. When we declare a variable to refer to a list of integers, we specify the type as `List<Integer>`.

```java
// note we don't need <Integer> on the right since it is implicit
ArrayList<Integer> ma = new ArrayList<>();
ma.add(1);
Integer my_item = ma.get(0) + 5;
```

The `<Integer>` specifies that we're working with an `ArrayList` containing only Integers: we don't need to do any casting.

Note that primitives cannot be passed as type variables; the wrapper class must be passed. This is due to the way that Java handles types under the hood (See Type Erasure).

# Custom Generic Classes

The basic syntax to define a generic class is as follows:

```java
public class Box<T> {
    private T item;

    public void set(T item) {
        this.item = item;
    }

    public T get() {
        return item;
    }
}
```

In this example,
- `Box<T>` is a generic class, with `T` being the type parameter.
- You can create instances of `Box` for different types, like `Box<Integer>` or `Box<String>`.
- The type `T` is replaced with the actual type when the class is instantiated.

```java
Box<Integer> intBox = new Box<>();
intBox.set(123);
Integer value = intBox.get();

Box<String> strBox = new Box<>();
strBox.set("Hello");
String text = strBox.get();
```

Generics can also be defined on methods

```java
public <T> void test() {
	...
}
```

# Bounded Type Parameters

You can also **restrict** the types that can be used with a generic class or method using **bounded type parameters**. This is useful when your code relies on certain behaviours or interfaces being available.

For example, Java’s `Collections.sort()` method requires that the elements in the list implement the `Comparable` interface, so that they can be ordered. 

If we wanted to define a generic method that requires its type parameter implement Comparable, we might write

```java
public static <T extends Comparable<T>> void sortList(List<T> list) {
    Collections.sort(list);
}
```

In this example:

- `<T extends Comparable<T>>` means that `T` must be a type that implements `Comparable<T>`.
- This ensures that the `sortList` method can safely call `compareTo()` on elements of the list.

If you try to call `sortList()` with a type that doesn’t implement `Comparable`, you’ll get a compile-time error. 

## Wildcards

It turns out that our `sortList()` is actually _slightly_ more restrictive than it needs to be. If we look at the signature for `Collections.sort`, it is actually:

```java
public static <T extends Comparable<? super T>> void sort(List<T> list)
```

`<T extends Comparable<? super T>>` means that `T` must be a type that can be **compared to itself or any of its supertypes**.

The `?` is a wildcard that stands for an unknown type. We use it here because we don't care about the specific type passed to Compared; we only care that it is a superclass of `T`. This allows the method to work with a wider range of types, especially when inheritance is involved.

If the signature were just `<T extends Comparable<T>>`, it would fail in cases like this:

```java
class Animal implements Comparable<Animal> { ... }
class Dog extends Animal { ... }

List<Dog> dogs = new ArrayList<>();
Collections.sort(dogs); // works with Comparable<? super T>
```

This works because `Dog` is a subtype of `Animal`, and `Animal` implements `Comparable<Animal>`.

We can also use wildcards with `extends` or `super` as generic types when declaring variables.

In general, wildcards with super are generally used for types that will be modified by the method/class. For example, we could write

```java
List<? super Dog> dogs = new ArrayList<>();
```

to allow for lists of Dogs or any if its subclasses. Java knows that the type will be `Dog` or any of its superclasses, so it is safe to add `Dog` or any of its superclasses.

```java
dogs.add(new Dog());       // OK
dogs.add(new Puppy());     // OK (Puppy extends Dog)
// dogs.add(new Animal()); // Compile Error! The list could be a List<Dog>, which cannot hold a generic Animal.
```

However, if you try to pull elements out of a `? super Dog` structure, Java cannot guarantee the exact class type you are retrieving except that is it at least `Object`; wildcards with super is not ideal for reading/consumer data.

The opposite is true for wildcards with extends; we could write

```java
List<? extends Dog> dogs = new ArrayList<>();
```

When we try to pull an item out, Java can guarantee that it is a `Dog` or a subclass of `Dog`. However, you cannot write any concrete object into it, since Java doesn't know the exact underlying type of the list; you cannot add a `Dog` since the generic type could be a subclass (e.g. `Puppy`).

```java
// dogs.add(new Dog());    // Compile Error!
// dogs.add(new Puppy());  // Compile Error! (Even adding a Puppy fails, because the list could be a List<Chihuahua>)

dogs.add(null);            // OK (null is the only exception because it fits any reference type)
```

Java developers rely on the PECS mnemonic:
* **P**roducer **E**xtends: Use `? extends T` if your generic structure primarily reads (produces) data.
* **C**onsumer **S**uper: Use `? super T` if your generic structure primarily writes (consumes) data.

# Type Erasure

Under the hood, Java generics use a technique called **type erasure**. This means that generic types are replaced with `Object` at compile time, and the compiler inserts casts where necessary.

So while generics give us type safety at compile time, the JVM doesn't retain generic type information at runtime — it just sees regular classes and `Object` references. This is why you can't do things like `new T()` or check `instanceof T` — the type information isn't available at runtime.
